## 2 管理

### 2.1 配置管理机构

| 角色 | 职责 |
|------|------|
| 配置管理员（PM） | 审批基线变更、管理发布版本、维护配置项清单 |
| 开发组 | 日常提交、遵循分支策略、填写 SPR |
| 文档组 | 文档版本控制、交叉引用一致性 |
| 测试组 | 验证配置项完整性、冒烟后签署 |

### 2.2 Git 分支策略

```
main          ← 稳定发布（竞赛提交、基线冻结）
  └─ develop  ← 日常开发集成
       └─ feature/*  ← 功能分支（如 feature/gate-policy）
       └─ fix/*      ← 缺陷修复
       └─ docs/*     ← 文档修改
```

**分支规则**：

- `main` 只接受经 code review + 冒烟测试通过的 `develop` PR 合并。
- `feature/*` 从 `develop` 分出，完成后合并回 `develop`。
- 提交信息格式：`type(scope): description`（如 `feat(algo-viz): add Dijkstra step-by-step animation`）。
- 提交粒度：单次提交对应单一逻辑修改，避免「大量更新」式提交。

### 2.3 版本号约定

| 版本号 | 格式 | 示例 | 说明 |
|--------|------|------|------|
| 大版本 | VX | V1 | 竞赛提交级别 |
| 功能增量 | VX.Y | V1.1 | 挑战赛增量 |
| 修复补丁 | VX.Y.Z | V1.0.1 | 文档/配置修正 |

## 5 变更控制

### 5.1 变更流程

```
提出变更请求 → CCB 评估影响 → 批准/拒绝 → 实施 → 验证 → 更新基线
```

### 5.2 竞赛提交期策略

- **功能冻结**：不接受新功能合入，仅接受缺陷修复。
- **文档补全**：截图嵌入、命名统一、交叉引用修复视为文档补丁，可不走 CCB。
- **紧急修复**：部署健康检查异常、密钥泄露等安全类变更可直接实施，事后补 SPR。

### 5.3 配置变更请求模板（SCR）

| 字段 | 说明 |
|------|------|
| SCR 编号 | 自动递增（SCR-001 起） |
| 变更配置项 | 受影响的 CI/CD 编号 |
| 变更描述 | 什么变了、为什么 |
| 影响范围 | 代码 / 文档 / 部署 / 测试 |
| CCB 决议 | 批准 / 拒绝 / 修改后重提 |
| 实施人 | 执行变更的开发者 |
| 验证人 | 验证变更后再审的人员 |

### 5.4 软件问题报告模板（SPR）

| 字段 | 说明 |
|------|------|
| SPR 编号 | 自动递增（SPR-001 起） |
| 发现阶段 | 开发 / 测试 / 部署 / 评审 |
| 问题描述 | 可复现步骤 + 预期 vs 实际 |
| 严重程度 | 致命 / 严重 / 一般 / 建议 |
| 关联配置项 | 受影响的 CI/CD 编号 |
| 解决方案 | 简述修复措施 |
| 修复版本 | 修复所在版本号 |
